# Formation bond 最大羁绊求解器：精确算法设计

状态：礼装优先的精确快路径、通用分支定界回退、可取消的原生平台进度流、独立 Formation Bond 页的 Input／Results 标签及验证用例已实现。本文是算法的设计依据。礼装重复性规则已按本轮讨论整理为 §2.2：特性礼装、两个等价组及两个指定 ID 受限，普通 5%／2.5%／2% 可重复。身份分组、两条算法的容量／匹配、代表分配、固定冲突提示及纯算法回归已同步。无论使用哪条路径，都必须依 `provenOptimal` 区分已证明的最大值和最佳已知队伍。

读者：实现、评审和测试此功能的开发者。本文同时定义求解语义、预处理、搜索、结果接口和可验证的正确性条件。

## 1. 目标和正确性合同

每次求解以当前选定的 `QuestPhase`、六个编队位置、活动与位置设置，以及求解器筛选和 COST 预算作为固定输入，返回最大可行队伍总羁绊。标签页可在两次求解之间重新选择关卡。求解始终按茶壶 ×1；UI 只在显示时乘茶壶倍数。

`provenOptimal=true` 的含义是：全部可行队伍均已搜索，或被有证明的上界排除；输出的队伍可实例化为互不重复的自有从者 ID，礼装满足 §2.2 中各类型的身份约束，并用手动计算语义复算得到相同分数。到达节点预算只能返回 `provenOptimal=false` 的最佳已知**可行**队伍，绝不能称其为最大值。

规则提取以手动页为基础，并采用本求解任务明确的范围：自由礼装候选只取**全队生效、与佩戴者无关**的效果；活动限定的自身礼装效果不进入自由候选；从者活动被动只计入自身效果。固定礼装仍需按手动页计算其真实效果，避免把已固定成员悄悄改写。忽略全队从者活动被动的队伍与手动页可有预期差异；`provenOptimal` 只对本节定义的求解范围成立。若今后手动页扩展其他目标范围，求解器必须同步扩展或显式报不支持。

## 2. 规则语义

### 2.1 位置与固定维度

每个位置分别固定或搜索从者、equip1。“最多冠位数量（不考虑助战）”下拉框提供 0–5，`maxGrandServants == null` 时按关卡推导默认值：普通关卡 0、戴冠/研钻战 1；有明确生效位置时，排除初始支援位置后计数（上限 5），例如终章追忆战 5、新章 5000108/2 为 2。切换关卡清除手动覆盖。

自由候选按当前账号 `favorite && grandSvt` 区分冠位身份。在关卡启用冠位、位置允许且数量上限大于 0 时，自动选入的冠位搜索 equip3。位置优先读 `isUseGrandBoardInitPos`，缺失时读 `activeGrandBoard`；未提供明确位置的冠位关卡沿用普通戴冠战规则。初始支援位置不作为自有冠位候选位。通用搜索把自有冠位人数作为独立容量约束，固定和自由自有冠位共同计数，助战不计入。固定成员超过上限时无可行解。

equip3 不计 COST，固定冠位保留原有固定/搜索行为；自由位置残留的冠位标志和 equip3 不作为固定选择。应用结果保留自动冠位身份。equip2 不参与羁绊礼装计算。自由冠位的额外位依赖从者，礼装优先路径在此情况下回退通用精确搜索；从者分组保留冠位身份，礼装剪枝容量包含潜在额外位。

只固定 equip1 的位置仍搜索从者；固定礼装与所选从者的佩戴者条件必须一起求值。固定从者不受自由候选筛选；固定礼装也不受自由礼装排除条件影响。固定从者不满足关卡特性限制时，搜索前的 `validateFormation` 抛出含位置／从者 ID 的 `BondServantRestrictionError`，页面在切换结果 Tab 前弹窗显示冲突从者与现有 `QuestRestrictionDescriptor` 的限制说明；不会启动搜索或只显示 Failed。某位置没有合法 item 时，预处理报错；固定自有从者的重复 ID 等冲突由具体身份匹配判为无解；受限固定礼装的重复须在搜索前提示队伍不合法；无羁绊效果的固定礼装允许重复。

`svtBonus[position].addRate/addValue` 作用于该位置实际存在的从者。`isBond15` 与 `isBondReachLimit` **仅对编队固定的自有从者有效**：前者提供全队 +250 RateCount，后者令该位置得分为零，但不删除它提供的全队效果。自由位置忽略这两个标志。助战位置忽略两者。

所有标为助战的位置均用无特性的虚拟从者替代。助战不产出羁绊、不消耗 COST、不占自有从者或礼装容量；只搜索未固定的助战 equip1。该位置标记 `grandSvt` 且关卡 `isUseGrandBoard` 时，equip3 与自有冠位位同样参与搜索（未固定则枚举自由助战礼装类，已固定则计入其固定效果）；未标记或非 Grand Board 关卡时 equip3 一律忽略。同一助战的 equip1／equip3 按 §2.2 处理受限身份，不与自有礼装的身份池混用；无羁绊效果的礼装不做重复检测。助战礼装的佩戴者条件对空特性求值，目标条件仍对实际队伍目标求值。前排每个助战提供全队 +40 RateCount；前排自有从者仅自身 +200，均受 `frontlineBonus` 开关控制。多个助战按手动公式逐个计入，不依赖“最多一个助战”的旧假设。

未固定的 equip1 或生效的 Grand equip3 可以选择为空，即使该位置的从者已固定；空 equip1 不消耗礼装 COST，不能为了搜索效率强制每个从者穿礼装。固定 equip1 与生效的固定 equip3 保留，预算不足时不能自动卸下它们来构造可行队伍。礼装为空和从者为空是独立选择；只固定从者时，仍可保留从者而不穿礼装。

### 编队位置上限与默认关卡

`maxServants` 默认 6，允许 1–6，包含助战；只使用前 N 个位置。后续位置不产生从者、equip1/equip3、COST、Bond 15 或前排助战加成，两条算法都在构造输入时截断可用位置。结果应用到六位置编队时清空尾部，不能仅在页面删除固定选择后仍让求解器自动填入尾部。

修改人数上限不会立即破坏编队。点击 Solve 时若尾部存在从者、助战、equip1/2/3、Grand 或自定义羁绊设置，先确认清空；取消不搜索；确认后清空整位置并刷新输入页，再切换 Results 并等待切换动画后求解。纯空位置无弹窗。

仅 `FormationBondOption` 新建构造函数使用硬编码默认关卡 94137202/1。已有保存的 0/空引用不迁移，显示原值。关卡选择行优先显示已加载 QuestPhase；加载期间用配置 ID/phase、本地 Quest 名称及 BasicQuestPhaseDetail 基础羁绊预览，缺失数据用横杠。失败保留 ID 供重试，Solve 仍要求完整 QuestPhase；无效 ID 不发请求。

### 助战位置不会被自动推断

某个位置是否为助战只能来自用户设置。`BattleTeamFormation` 的构造、`toJson`/`fromJson` 往返、`BattleTeamSetup.toFormationData()` 都不得为空位补出 `SvtSaveData(supportType: friend)`。助战可以放在任意位置、也可以一个都没有，因此不能按“第三位是助战位”的旧假设回填——否则把助战放在别处且第三位留空时会多出一个助战，完全没有助战时同样会被凭空加上。

“第三位默认放助战”只在明确的初始化点声明：`BattleOptions.formation` 新建时把 `svts[2]` 设为 `SupportSvtType.friend`（战斗模拟），羁绊页在全空编队首次打开时对 `option.teamFormation` 做同样处理（`formation_bond.initState`）。`PlayerSvtData.isEmpty` 已把“标为助战但没有从者”视为非空，`toFormationData()` 因此能忠实保留助战标记，无需再补。

### 2.2 COST、筛选和唯一性

预算默认为 `ConstData.userLevel[ConstData.maxUserLevel]!.maxCost`；`maxUserLevel` getter 已存在。自有位置 COST 为该灵基的 `overwriteCost ?? cost` 加 equip1 礼装 COST；固定与自由位置都计入，助战及 equip3 不计入。

自由从者候选可按当前 region 是否实装、favorite、`bond >= X` 和自定义 ID 排除；自由礼装可按 region、自定义 ID 排除，并按 `favoriteSvtEquipOnly` 只保留持有（`CraftStatus.favorite`，即 owned）的候选。该开关只作用于自有位礼装：助战是借来的，玩家的持有情况与它无关，因此助战礼装不受持有筛选限制，但仍受 region 与自定义 ID 排除约束。实现上持有判断并入自有可用性判定（`_loadFreeCesSteps` 的 `canOwn`），不能写在礼装级别的 `continue` 里，否则会连助战候选一起砍掉。

从者与礼装是两个独立开关（`favoriteSvtOnly` / `favoriteSvtEquipOnly`，旧 `favoriteOnly` 键迁移为 `favoriteSvtOnly`）。`favoriteSvtOnly` 开启时，队伍页选从者传入 `PreferPlayerSvtDataSource.current`（携带账号实际等级/羁绊/冠位数据），关闭时传 `none`。选从者后若账号数据中该从者为 favorite 且 `grandSvt` 而当前槽位未标记冠位，弹窗确认是否标记（`svt_selector._confirmGrandSvt`）；数据来源为 current 时通常已自动标记，不再弹窗。固定成员不被过滤。region 发布表缺失时不能把“未知”当成“已实装”：返回明确的数据不可验证状态，或在 UI 中要求关闭此筛选。

### 候选规模报告

`BondSolverResult.candidateSvtIds` / `candidateCeIds` 供结果页顶部显示本次求解实际可用的候选数量，两者都取自原始候选池（等价归并**之前**），因此不受 `pruneDominatedCes` 影响、也无需依赖剪枝的执行时序。候选礼装只统计带条件的（`CeBondEffect.hasCondition`）：无条件礼装彼此可互换，求解器对它们只保留一个代表，报告出来恒为 1 且没有意义；助战礼装不计入，见上一节。

两者为 `null` 表示队伍没有对应的自由位、候选池从未构建——这与“构建过却为空”的 `0` 是不同状态，前者 UI 应整行隐藏而不是显示一个误导性的 0。筛选或关卡改动会把结果整个清空（`formation_bond.clearResults`），候选行随之消失，无需另行标记过期。

关卡中所有 `RestrictionType.individuality` 条目按 `Restriction.checkSvtIndiv` 的 `equal`/`notEqual` 语义逐一判断。从者特性取当前 Quest EventId 与所选灵基下的有效 individuality；自由候选在按特性/COST 去重**之前**筛选，避免合法灵基被错误合并。固定自有从者不受用户设置的排除筛选。`searchFixedAscensions` 默认开启，此时输入灵基不满足关卡限制则报错；开启时固定 ID 并枚举普通灵基及灵衣，按各灵基判断特性、COST 与限制，只要存在合法灵基即可求解。固定礼装、Bond 15／上限与 Grand 标志保留；虚拟助战没有可验证的实际从者，不进行此项检查。其他 restriction 类型目前不在本求解器支持的编队约束范围内。

关卡输入与恢复优先读取 `db.gameData.getQuestPhase(id, phase)`；本地数据中只有 Grand Board war 关卡需要组队特性限制，本地 phase 的 `restrictions` 按原样使用，普通关卡缺少该字段不意味着需要补请求。输入关卡 ID 并选定 phase 时，只有本地没有该 phase 才通过 Atlas API 加载；连 Quest 元数据也不在本地时，先加载 Quest 再选择 phase。输入加载失败保留原选择并提示错误。恢复时也先本地后 API，恢复完成前不能 Solve。Solve 再检查当前 QuestPhase 已存在，优先复用同 ID／phase 的本地对象，否则使用输入阶段已加载的对象，不因本地缺少 `restrictions` 强制刷新 API。

Formation Bond 是独立于 Bond Bonus 查阅页的模块，提供 `Input` 和 `Results` 两个标签。`User.formationBondOption` 是编队、活动、前排、茶壶、COST 和从者／礼装筛选的唯一持久化配置。默认页面直接引用当前用户的该对象，不在加载时复制；若队伍六个位置均为空，第三位置预设为空助战（`SupportSvtType.friend`）。外部调用方若需临时配置，先深拷贝用户配置、覆盖关卡和编队等字段，再以 `FormationBondPage(option: ...)` 传入；页面直接使用该对象，不写回 User。空助战位须能完整序列化。

页面编辑会立即改变所持有的配置对象；`saveData()` 在离开页面时把运行时编队和关卡写回该对象。对默认页面（`userBacked`），每次共享输入编辑（`updateSharedInput`）与茶壶倍数修改都调用 `db.notifyUserdata()` 标记脏数据，由 10 秒去抖保存落盘；离开页面时若已恢复完成，再显式 `db.saveUserData()` 兜底——web 关标签页／刷新没有生命周期保存，仅靠去抖会丢近期编辑。点击 Solve 且 QuestPhase 已准备成功后同样显式保存。由于默认页面持有 User 中的同一对象，其他途径保存 UserData 时，也可能提前持久化已编辑字段；当前实现不提供“点击 Solve 前绝不落盘”的隔离保证。求解时复制一次当前配置，并覆盖为运行时编队和已加载关卡，形成不受随后 UI 编辑影响的搜索输入；算法直接读取其中的 COST 和筛选字段。结果只在当前页面展示，不持久化。切换用户后需重新建立该标签的状态，不能把前一个用户的配置写入新用户。

同一自有从者 ID 在全队最多出现一次，即使它的不同灵基属于不同效果类。这条从者约束与下述礼装规则独立。

### 礼装重复性规则

“固定／空位”只看该礼装槽是否已指定礼装，与从者是否固定无关。**单个身份最多一张，不等于整个效果类最多一张**。自有身份池覆盖参与求解位置的 equip1 与生效的 Grand equip3；equip2、不生效的 equip3 和位置上限外的槽不参与。助战与自有独立，可以各带一张相同身份的礼装；同一助战自身的 equip1／equip3 仍检查受限身份。

| 礼装类型 | 自有固定位置 | 自有空位自动选择 |
| --- | --- | --- |
| 无羁绊效果，如 9408940 | 同 ID 可重复，不检查 | 不进入自由羁绊礼装候选 |
| 普通通用全体 +5%、+2.5%、+2%（不含下列指定 ID／组） | 同 ID 可重复，不检查 | 同代表 ID 可重复，不按不同 ID 数限制张数 |
| 有目标特性要求的羁绊礼装 | 同身份重复则提示队伍不合法 | 避开固定占用，同身份最多一张 |
| 英灵肖像 +50，CollectionNo 99–108 | 整组最多一张 | 整组最多一张，并避开固定占用 |
| 英灵逢魔，FSN 从者 +10%，CollectionNo 1973–1979 | 整组最多一张 | 整组最多一张，并避开固定占用 |
| 9403520，我方 +5%／助战 +15% | 此 ID 最多一张 | 此 ID 最多一张，并避开固定占用 |
| 9401970，全体 +10% | 此 ID 最多一张 | 此 ID 最多一张，并避开固定占用 |

特性条件指羁绊效果对接收从者的特性要求；Quest／Event 限定或助战专用倍率本身不等于特性条件。礼装同时含通用项与特性项时归入特性礼装。是否恰好存在受益从者不改变礼装身份；效果是否实际生效仍逐项按真实条件判断。9403520 虽然自有位只提供 5%，仍按指定 ID 限制，不能落入普通 5% 的可重复类。

#### 身份与等价组

普通与满破共用同一身份。特性礼装通常按具体 ID 限制，显式等价组则按组身份限制：同 ID 重复、同组不同 ID 共存，都属于重复。两个组内成员在羁绊求解上完全等同，不因卡面不同产生额外名额。对应游戏数据 ID 为：

```text
英灵肖像（99–108）:
  9400970, 9400980, 9400990, 9401000, 9401010,
  9401020, 9401030, 9401040, 9401050, 9401060
英灵逢魔（1973–1979）:
  9308100, 9308110, 9308120, 9308130, 9308140, 9308150, 9308160
单 ID 限制:
  9403520, 9401970
```

`bond_rules.dart` 的 `BondCeIdentity.families` 包含上述两组；`uniqueIds` 单独配置两个受限 ID，不把“任意 10% 效果”推断为永远只有一个名额。未来出现不同 ID 的 10% 礼装时，是否同组需单独定义。1972 不属于英灵逢魔组。CollectionNo 108（9401060）的 +50 全体范围修正继续保留，不能因原始数据错误把它拆出英灵肖像组。

每个等价组自由候选只保留一个代表，沿用既有组代表策略：在满足筛选的成员中优先选择用户持有（favorite）的最小 ID，无持有成员时选最小可用 ID；开启“只选持有礼装”且整组无人持有时，自有候选不可用。排除任一成员即排除整组自由候选，不删除固定成员。固定成员保留具体 ID，不改写成代表 ID。

英灵极点（CollectionNo 2513–2532）属于可重复获得的普通全体 +2% 礼装，不属于身份等价组。它与普通 5%／2.5% 同样可在固定和自由位置重复使用代表 ID；排除只针对所选 ID，不扩展到其他同效果礼装。

#### 固定输入与自动补位

受限固定礼装先做重复验证，重复时明确提示队伍不合法，并指出冲突位置／礼装；不启动搜索，也不把它包装为搜索完成后的“无可行队伍”。验证通过后，其身份登记为自动选择的禁用项。普通 5%／2.5%／2% 与无羁绊礼装不登记。

```text
restricted(ce) = hasRecipientTraitBondEffect(ce)
                 or ce.id in explicitlyRestrictedIds
                 or ce.id in anEquivalenceGroup
reserved = set()
for each fixed owned CE where restricted(ce):
  if identity(ce) in reserved: reportInvalidFormation() // before search
  reserved.add(identity(ce))
added = set()
for each automatically selected owned CE where restricted(ce):
  if identity(ce) in reserved or identity(ce) in added: reject this selection
  added.add(identity(ce))
// Non-bond CEs and ordinary generic 5% / 2.5% / 2% CEs do not participate.
```

每个允许存在的佩戴实例仍独立保留实际效果、COST 与展示数据，效果归并不能丢失份数。普通 5%／2.5%／2% 可用同一代表重复佩戴，不受可用不同 ID 数量限制，只受可用装备槽、COST 等约束；固定的普通通用礼装也不减少自动选择名额。代表仍须满足自由候选的 region、持有、自定义排除等筛选。

#### 实现边界

`requiresUniqueOwnedIdentity` 只对显式组、指定 ID 或含接收者特性条件的羁绊函数返回 true，并按 CE 对象缓存。其余自由通用候选是可重复代表。分类检查所有原始技能，避免普通／满破或 Quest 激活条件改变身份。两条路径与结果转换共用以下边界：

1. `validateFixedCes` 在候选预处理前验证受限固定身份；发现冲突抛出携带位置、equip 槽与 CE ID 的 `BondFormationException`。页面在切换结果 Tab 前通过统一 `validateFormation` 执行礼装与固定从者的关卡特性校验，用已有本地化文案和限制描述组件弹窗列出原因，不启动搜索。固定从者校验与实际求解共用实装参考、有效特性和允许灵基范围；开启固定灵基搜索时，只要任一允许灵基合法就通过。助战按各自位置使用独立身份池。
2. 特性／指定 ID／等价组参与身份匹配与固定占用排除；普通通用代表不建立互异 ID 维度。`_ItemPayload.matchCe1Identity/matchCe3Identity` 使普通代表与受限 equip1／equip3 混合时仍能正确展开。
3. `_CeClass.repeatable/capacity` 区分类容量，普通类按本次可用槽数截断，受限类按不同身份计数；礼装优先枚举也允许普通代表重复，具体匹配不消耗它的身份。不能按普通类内不同 ID 数截断。
4. 普通通用类在效果、COST 和助战行为相同的类内只保留最小可用 ID 并允许复用，保留固定具体 ID；组代表先经过实装筛选再优先选持有成员。助战两个槽位的选择、替换和规范化同样区分可重复与受限身份，并避开固定的另一个槽。自由候选池的加载必须计入 Grand 助战的空 equip3，即使所有 equip1 都已固定。
5. 礼装优先路径、通用路径、候选替换、支配剪枝与上界使用同一容量模型。支配删除按不同受限身份数量计替换容量，或由一个可重复的支配类提供全部槽位的替换；不能把组内 10／7／20 个 ID 当成多个替换名额。

### 实装参考与灵衣特性

`FormationBondOption.releaseReference` 使用 `BondReleaseReference` 五项枚举：JP、CN、TW、NA、关卡关闭日期，默认 JP，不跟随当前 User 或显示语言。JP 使用默认数据库，等同不限制实装；CN/TW/NA 使用所选服 `entityRelease` 同时筛选自由从者与礼装。固定输入不受候选实装过滤；不为与羁绊无关的 `ce.region` 添加专属规则。求解 API 不再另传 Region。

日期模式对自由从者使用 `ServantExtra.getReleasedAt()` 的 JP 日期：大于关卡关闭时间才排除，未知日期保留。该日期表不完整且存在按 CollectionNo 回退，因此不能声称精确还原历史实装。礼装无实装日期，灵衣特性无添加时间，两者暂用默认 JP 数据；UI 以英文小字说明 `CE availability and costume traits currently use JP data.`。选项直接显示 JP 时区下的关闭日期。关卡未选择、关闭时间为 0 或达到永久开放阈值时禁用日期模式，原已选日期模式自动回退 JP；直接调用算法同样回退。

`BondReleaseRules.traits` 复制基础灵基特性后添加原有活动/灵基特性，再按所选 Region 的 `svtTraitRelease` 移除未实装的 `hasCostume`。JP 与日期模式保留默认特性。手动计算、求解器、可替换灵基判定、礼装贡献详情共用此逻辑，不修改共享数据库，不额外过滤未实装灵衣灵基本身。修改参考会取消搜索并清空旧结果，与其他共享输入一致。

### 2.3 羁绊公式与效果提取

对每个产出羁绊的自有位置，严格按 `SvtBondBonusResult.totalBond`：

```text
first  = floor(baseBond * (1 + frontlineRate / 1000))
second = floor(first * (1 + min(totalRate, maxFriendShipUpRatio) / 1000))
bond   = second + totalValue
```

叶节点使用与 `calcFormationBondResults` 相同的 Dart `double`/`floor` 顺序。上界可以采用更保守的整数向上取整，但不能用近似值作为最终得分。

每个 `servantFriendshipUp` 函数提取 `scope`（仅 `self` 或 `ptFull`；其余 scope 无效）、`rate`、`value`、佩戴者条件、目标条件、Quest 条件、EventId、助战 `followerVals` 与 `ApplySupportSvt` 规则。`actIndividuality` 和 `vals.Individuality` 分别对佩戴者判断；`overWriteTvalsList` 优先于 `functvals`，对目标判断。自我效果的目标就是佩戴者。固定礼装仍保留定向的 **RateCount 和 AddCount** 及佩戴者条件；自由礼装只保留全队生效且与佩戴者无关的候选，但可以针对**接收者**特性。

活动技能仅在 `enableEvent` 时计算；按手动页的 Quest 时间/EventId 条件、`extraPassive.num` 分组最高 `priority` 解析，并跳过技能 970663。解析后只计入 `self` 效果；所有从者活动被动的 `ptFull` 效果都不进入求解器。已启用的 campaign 按 `targetIds` 和 `calcType` 给目标从者加成；campaign 开关独立于 `enableEvent`。礼装函数的 EventId/Quest 条件始终按当前 Quest 判断。

### 2.4 可比较性边界

手动页接受真实助战从者；本求解器按需求用无特性虚拟助战，因此含真实助战的全固定队伍只在把手动页助战替换为同一虚拟语义后比较。除此之外，全固定队伍须逐位置、逐项效果与手动页一致。

### 2.5 从者全队活动被动

用户限定只考虑从者自己的活动羁绊加成。数据中非玛修从者的 `ptFull` 羁绊被动均为技能 970663（手动页原本就跳过）；其余全队活动被动来自玛修（`collectionNo == 1`）。因此按 `scope == self` 过滤所有从者活动被动，既实现该限定，也无需维护玛修的技能 ID 名单。此处是与手动页有意的语义差异，差分测试要单列说明。

## 3. 数据模块与预处理

模块接口：`FormationBondSolver.solve(...)` 与 `solveAsync(...)` 使用相同的命名参数，包含 Quest、编队、同时承载手动与求解筛选设置的 `FormationBondOption` 和搜索预算。预算在礼装优先路径计已评估礼装组合，在通用路径计搜索节点；两者都不改变 `provenOptimal` 的语义。`solveProgressively(...)` 没有节点预算参数：原生平台在工作 isolate 中先发可行改进、后发证明结果，取消订阅即终止 isolate；Web 按时间预算续接同一个可恢复搜索流程，含组合枚举、上界排序、从者 DP、通用准备与 DFS，不再从头重跑。`solveSteps` 与同步 API 共用流程；进度 API 的 `useWorkerIsolate`、`useCeFirst` 与 `useStreamingCeFirst` 可在纯算法测试中选择执行方式/算法。`useStreamingCeFirst` 强制可分离问题走流式路径，不绕过可分离性检查，也不添加用户配置。`BondSolverResult` 包含最佳已知具体队伍、`provenOptimal`、最高分同分代表 `ties`、跨分数档的有限候选 `candidates`、耗时与搜索步数；`isCeFirst` 标识礼装优先路径，`possibleCombinations` 在该路径的组合准备完成后才有值；首解可在总数仍未知时先回传。`best=null && provenOptimal=true` 表示无可行队伍；`best=null && provenOptimal=false` 表示尚未找到可行队伍。

同步、异步与渐进入口共用准备流程：先建立候选、等价类、贡献矩阵和固定 COST，再判断 CE-first 可用性；只有通用回退才物化自有从者×礼装的 item 乘积。`itemCount` 保持原理论候选数量口径，自有位通过类数直接计数；助战仍复用其合法选项生成逻辑计数。原生 worker 只接收选中算法的问题。

逻辑活动绑定在每次求解中以 `quest.logicEventId ?? 0` 延迟解析一次，礼装普通/满破、自有/助战效果及从者活动被动共用 solver 的请求内值。它不是 war/event 展示 ID；不得用其他 eventId 字段替代。显式零值同样表示已解析，不能触发重新查询。每次新求解重新取值；未提供预解析值的通用效果解析调用仍按传入 Quest 计算，不使用跨请求缓存。

当前实现按每次请求重建候选及效果矩阵，没有跨请求的数据集缓存。可以按两层理解预处理；第一层缓存仍是后续性能优化，而非已有机制：

1. **数据集层（规划）**：按游戏数据版本缓存各从者合法灵基的特性与 COST、礼装普通/满破效果原子、发布表。数据更新时失效。
2. **请求层**：套用 Quest、实装参考、筛选、活动、固定维度；解析有效效果与固定来源；建立从者候选、礼装候选、有效目标轮廓和贡献矩阵。只搜索羁绊相关礼装与“不佩戴”。

从者候选首先是 `(svtId, limitCount)`。两个候选只有在 COST、活动自身加成、campaign 加成、作为所有相关效果来源的行为、作为所有相关效果目标的行为、佩戴每个可用礼装后的自身效果都相同时，才进入同一 `SvtClass`。比较的是完整规范化向量，不仅是哈希或原始 indiv，也不能把不同 campaign 目标合并。每类保存成员具体 `(svtId, limitCount)`；同一 ID 可出现在多个类中，故类容量只是局部快速检查，最终还需 ID 匹配。

礼装候选首先是 `(ceId, limitBreak)`。自由自有候选要求当前 Quest 生效的羁绊效果全部是 `ptFull`，且 `actIndividuality`、`vals.Individuality` 均无佩戴者条件；针对接收者的特性条件可以保留。自有礼装按对全部目标轮廓的 `(RateCount, AddCount)` 贡献、COST 及助战效果向量归入 `CeClass`，equip1 与可用的 equip3 共用自有类，但只有 equip1 计 COST；助战礼装按 `followerVals` 贡献另建类。普通与满破版本如效果不同，都保留；若同一 ID 的两版效果相同，可保留其中一版作为显示代表；受限礼装的不同版本共用身份容量，普通 5%／2.5%／2% 则允许重复使用代表。无条件 +5%、+2.5%、+50 等**各自**归类，不能互相混为一类；归类后还须保留 §2.2 的身份／等价组／可重复策略，不能只由类内 ID 数决定容量。固定礼装仍按真实效果计算，不受自由候选筛选。

2026-09-19 数据审计发现四个带自身效果的礼装 ID：9404310、9405110、9407110 都有活动 EventId，自由候选排除；9401060「英灵肖像：大流士三世」的数据标为常驻 `self +50`。用户确认这是数据错误，应视作 `ptFull +50`。此修正在手动计算与求解器使用同一规则，且仅在原始 scope 为 `self` 时生效；若以后数据改正成 `ptFull`，不会重复加成。另两个活动礼装的全队效果还带玛修佩戴者条件，也因此不进入自由自有候选。新数据版本若出现其他自身或佩戴者条件的礼装，默认从自由候选排除，并保留固定礼装的真实计算。

`temp/fgo-calc` 的关键观察是：若礼装来源不依赖佩戴者，而且所选从者不会改变全队来源，先决定礼装组合，就能把每个从者的收益算成独立物品，再解从者 COST 背包。其无条件、同 COST 礼装优先级链可作为后续候选剪枝的思路，但须重新证明具体 ID、固定槽位与普通/满破共享 ID 时的可替换性；不能仅凭单个礼装效果更强就**删除整个弱类**：队伍可能同时需要两类。本实现只在以下充分条件同时成立时删除弱类 `B`：保留类 `A` 的 COST 不高于 `B`；对每个佩戴者和目标轮廓，`A` 的 team rate/value 分别不低于 `B`，且对佩戴者还覆盖 `B` 的 self rate/value；所有此类 `A` 合起来的可用替换容量至少等于全队可能占用的自有礼装槽数。容量按剩余受限身份去重计数（整个等价组只算一份），普通可重复类可按可用槽数计；不能拿组内不同 ID 数作为容量。使用 `B` 的队伍至多占用 `slots-1` 个其他名额，故必有一份可用替换。每删除一类就重新检查剩余类，避免循环支配证明。固定礼装计入槽数但不受筛选和删除影响。

对每种源物品与目标轮廓，预先算好 `(rate, value)` 贡献。固定来源也放入同一矩阵。搜索热路径只读整数数组/位集，不再遍历 `NiceSkill`、礼装技能或个体特性。

自由礼装池已过滤为 team 且无佩戴者条件，其自有/助战贡献各计算一次；对每个接收轮廓仍逐项判断目标条件。自有类保留原长度的 `byWearer`，各行引用同一只读贡献，rate/value 向量及共享行列表不可写。固定礼装继续使用原逐佩戴者构建路径，不能把其自身效果或佩戴者条件纳入这项复用。归类时每个向量只序列化一次，再按原行数重复签名，故类键的内容逐字保持，COST、自有/助战差异、身份策略、普通/满破归并和类成员顺序均不变。贡献计算和长期向量存储由逐佩戴者重复的平方量级降至线性；为保留原键，临时完整矩阵键的字符量仍可能为平方量级，不据此声称整个准备阶段的空间复杂度已线性化。

## 4. 搜索算法

### 4.1 礼装优先的精确快路径（已实现）

先检查本次请求是否**可分离**。可分离的充分条件是：所有自由自有礼装的全队效果与佩戴者无关，且其自身效果均为零；固定礼装穿在可变从者或可变灵基身上时，其全队效果与该选择无关；可变从者与灵基没有随选择而改变的全队效果。固定礼装的自身效果、活动对从者自身的加成、前后排倍率、目标特性和 campaign 都可留在从者收益函数中。助战礼装单独枚举，助战虚拟从者不进入背包。条件不成立时走 4.2—4.5 的通用精确搜索；绝不能让这条快路径静默忽略条件效果。

可分离时，以 `equip1` 与 Grand Board `equip3` 两种槽分别枚举**礼装效果类的重数**，不枚举类内 ID 的排列或等效自由礼装在槽位间的排列。自有从者仍按位置求解，因为前后排、固定维度和每位置加成可能不同。只给 `equip1` 的礼装计 COST；先验证受限固定自有身份没有冲突，再从自动候选中扣除其占用，对自动受限礼装做具体身份匹配。匹配失败即丢弃该组合。助战礼装的组合在外层单独枚举，先删去被另一助战选项逐目标 rate/value 支配的选项；助战 ID 不与自有礼装互斥。无礼装也是合法选择。固定来源、所选礼装与助战效果相加后，对每个自由位置和 `(svtId, limit, cost)` 用手动页的两次 `floor`、rate cap 与 AddCount **精确**计算得分。固定从者的得分同样在这一阶段计算。

固定灵基搜索开启后，固定自有 ID 的非等效灵基进入从者 DP，其位置必填、ID 不能替换；对应可变 COST 不再预扣为固定单值。若所有合法灵基对本次问题完全等效，保留一个代表并作为固定项，不增加 DP 位置维度。关闭该选项时固定从者继续单独计分与计 COST。

令 `F` 为需要选择从者或灵基的自有位置数，`C` 为剩余 COST。对每个 `(位置, 从者 COST)`，先按分数只保留前 `F` 个**不同从者 ID**，同一 ID 的同 COST 多灵基只保留该位置分数最高的灵基。理由：若某个被删候选在最优队伍中占该位置，则至少有 `F` 个同 COST、该位置得分不低的 ID；其他自由位置至多占 `F-1` 个，必有一个可替换。自由从者池先排除所有固定自有 ID；固定灵基池只包含该位置的固定 ID。这个缩减仅在自由从者不产生动态全队效果时成立；否则替换可能改变其他人的分数。

之后按从者 ID 做 0/1 动态规划：状态 `dp[occupiedPositionMask][cost]` 存最高得分和见证。处理每个 ID 时，只能跳过，或选择该 ID 的一个灵基放到一个尚空位置；用下一层 DP 写入，确保同一 ID 绝不入队两次。当前实现始终保留各自由位置的 mask 位；前排三个槽的从者排列不会在此路径额外商掉。**自由从者位置允许留空**：最终接受所有包含“固定礼装但自由从者”必填位，且已占用自由 equip1 槽数足以安放所选 equip1 礼装的 mask；空位得分为零，也不产生该位置的自定义加成。匹配 CE ID 后再把礼装分配给这些已占用的自由 equip1 槽。每个 CE 组合的最优值是固定位置得分加所有合格 `dp[mask][cost<=C]` 的最大值。不同组合的分数用全局 best 比较，同分结果按效果轮廓归类。若枚举与 DP 穷尽，才返回 `provenOptimal=true`。

上界仅依赖位置、接收轮廓与自身 rate/value，不依赖从者 ID 或 COST。每个位置先按 `(profile, selfRate, selfValue)` 去重上界接收者；对任意礼装来源向量，同组得分严格相同，故不改变组合上界。具体从者 DP 仍使用原始候选并检查 ID 与 COST，不能使用这份上界去重池。

物化排序与流式前缀共用完整评分域分组：位置的 `first`、固定/自由状态及同序接收者三元组列表完全相同时，对任意来源向量的最大分数也相同。固定状态参与键，因为自由位置的初始最高分是 0（允许空位），固定位置则是不可达哨兵，负分或空域时不可混用。助战和满羁绊零分位继续跳过。每次上界按组计算一次最高分，再沿原位置顺序相加，不通过乘组数改变求和顺序。组信息仅限本次请求，上界数值仍逐组合/前缀重算；精确从者 DP 不合并位置或候选。分组复用只减少重复计算，本身不收紧或放宽上界。

```text
combos = []; seeded = set()
for supportChoice in nondominatedSupportChoices:
  for ownCeCounts in canonicalMultisetsBy(equip1, equip3):
    if ceCost > remainingCost: continue
    ceIds = matchDistinctIds(ownCeCounts, fixedOwnedCeIds)
    if ceIds == none: continue
    sourceVector = fixedSources + supportChoice + sum(ownCeCounts * ceVectors)
    upper = fixedSlotScores(sourceVector)
          + sum(max(0, max score(sourceVector, svt) for svt in freePool) for freePosition)
    combos.add((upper, sourceVector, ceIds))
    if isIncreasingUpperRecord(combo) and size(seeded) < 2 and evaluationBudgetAllows:
      updateBestAndPublish(exactServantDP(combo)) // 先建立合法下界，不扩展同分队伍
      seeded.add(combo)
sort combos by upper descending
for combo in combos:
  if best != none and combo.upper <= best.score: break // 最大分已证明
  if combo in seeded: continue
  scores = exactSlotScores(combo.sourceVector, allServantVariants)
  candidates = topFDistinctIdsPerPositionAndCost(scores)
  dp = {emptyMask, cost0: 0}
  for servantId in candidates.groupById:
    next = dp                                 // skip this ID
    for state in dp:
      for (searchPosition, limit) in servantId.legalChoices:
        update(next[mask | positionBit][cost + svtCost], score)
    dp = next
  updateGlobalBest(dp[eligibleMasks] + fixedScore, combo.ceIds)
```

组合上界忽略 COST、跨位置从者 ID 唯一性、礼装实际安放条件，却逐槽取可行从者的最高精确分数，因此绝不低估该组合真实最优值。按上界降序评估后，下一未评估组合的上界若不超过当前可行分数，就已证明最大分；同分收集可继续，但不影响 `provenOptimal`。这里的 `cost` 状态还可按“相同 mask、COST 不高且分数不低”删除劣解，目前没有启用。不能把 `temp/fgo-calc` 对 15 绊的队外加法直接搬来：本需求的 15 绊只允许固定从者，且手动公式在倍率内部逐人取整。

从者 top-F 的每位置 COST／ID 分组只依赖请求内不变的候选变体，首次精确评估时分片构建，完整后才存入本次搜索的缓存。组间保留原 COST 首次出现顺序，组内保留 ID 首次出现顺序与各 ID 的变体顺序；同一 ID 的不同 COST 仍是不同组项。每个礼装来源向量仍重新评分，在同 ID／COST 的变体中只以严格更高分替换，保留原同分灵基；随后对与旧实现完全相同的输入序列执行原完整排序，再取前 F 个 ID。缓存不保存分数、最佳灵基或背包结果，也不跨请求共享；负分、上限零分与当前 COST 不可用的组按原规则处理。设各自由位置的变体数之和为 T，分组构建由每次评估的 O(T) 哈希工作变为请求内一次 O(T)，额外引用/组索引空间为 O(T)。每组合的评分和完整排序仍保留，最坏时间阶数不变。

无显式评估预算、需要多个候选且存在可变自有从者的流式搜索，会在证明后重访前缀以补充候选，因此允许请求内缓存最多 512 个精确从者分配。键包含完整 rate/value 来源向量、实际剩余从者预算及待安放 equip1 数；候选域、固定/必填位置、空位规则和评分条件均为本次问题的不变量。不合并仅“看起来相似”的向量，不跨请求复用。保存完整从者/灵基分配或已证明不可行的空结果，完成 DP/回溯后才发布，只读保存；缓存满后不新增条目，原有条目仍可命中。每个 CE 组合仍独立匹配具体礼装身份、累加来源并组装/复核队伍，不复用礼装身份或结果对象。单候选、有显式预算、物化路径及全部从者固定的请求绕过此缓存。

缓存命中也计为一次已经精确求值的 CE 组合，维持原发现顺序、补充组合额度和候选结果；实际 DP 执行次数另作性能统计。有显式评估预算的请求不使用该缓存，预算单位不变。键与保留分配额外空间为 O(512 × (R + F))；键构造为每次可缓存评估 O(R)，缓存表查找不消除来源累加、身份匹配与队伍组装。

自有 CE 身份匹配先按原有维度顺序（候选具体 ID 数升序）和 ID 数值顺序回溯，最多检查 128 个候选；超过上限必须切换算法，不能判为无解。回溯退出时完整撤销临时身份占用，再用二分图增广判断剩余受限维度是否可匹配。可匹配时沿原维度与 ID 顺序，逐个锁定第一个仍允许后缀完成的 ID，故返回的具体 ID 代表与原穷尽回溯完全相同，而非直接采用任意增广分配。匹配中的身份始终经 `BondCeIdentity.of` 规范化；固定受限身份保留占用，普通可重复类不占用互异资源，其不同具体 ID 不改变后缀状态，只需尝试最小 ID。空域仍不可匹配。物化枚举、有界探测与流式搜索共用此匹配器。若 `D` 为维度数、`A` 为这些维度的原始候选 ID 数之和，后备算法保守最坏界为 `O(D × A²)`，不会枚举所有身份排列。每个请求的不可变 CE 类只排序并缓存具体 ID 一次；额外保留空间为各类域大小之和，不跨请求复用，也不缓存匹配子问题。该改动消除单次身份匹配的排列退化，不保证整个组合搜索为多项式时间或单步严格满足调度时间片。

设 `M` 为通过容量、ID 和 COST 检查的礼装组合数，`E` 为真正评估的组合数（含最多两个提前评估的种子），`N` 为从者变体数，`R` 为上界去重后的接收者数，`F` 为需选择从者或固定灵基的位置数，`C` 为剩余 COST。构造上界约为 `O(N × F + M × R × F)`，最坏情形的背包部分为 `O(E × N' × 2^F × C × F × V)`，`N'` 是各位置同 COST 只留前 `F` 个不同 ID 后的数量。以 17 个自由自有礼装效果类、五个 equip1 槽为例，连同“不穿”，最多有 `C(22,5)=26,334` 个无序重数组合。当前实现按每类剩余身份容量计算 equip1/equip3 共享容量的无序组合数上界，再乘助战选项数；普通可重复类以可用槽数截断。计数在 250,001 饱和，上界仍忽略跨类共享身份与 COST。助战选项乘积 `S>1` 时物化阈值为 20,000，否则为 250,000；前者避免在支持选项放大的空间中支付全量上界/排序成本。超过所选阈值时先对自有礼装做有界探测，纳入 COST 和具体身份匹配，复用通过的组合；探测的自有存储上限按所选阈值除以助战选项乘积折算，保证完整物化组合不超阈值。探测超限时改用 §4.1.1 的流式搜索，不把规模大当作不可分离；这个阈值只选择算法，不更改最优性合同。自有礼装枚举在 equip1 COST 超预算时直接剪去其 equip3 扩展；Grand 的 equip3 仍免费。身份不可匹配的前缀不再扩展更多 equip3，因为增加身份维度无法修复已有冲突。种子优先评估不丢弃任何未评估组合；排序后跳过已评估种子，其余组合仍须精确评估或被安全上界排除。预算中断时只返回已匹配 ID、已复算分数的可行队伍，且 `provenOptimal=false`。

物化路径保留助战选项在外、自有 CE 组合在内的遍历顺序。自有枚举只依赖请求内固定的槽数、COST、类容量、候选域和固定身份；助战使用独立身份池，其来源向量仍在每个完整组合中重新加入。因此存在多个助战选项且没有准备期探测结果时，第一次自有枚举边生成边送入上界/种子评估，并收集其完整选择；遍历完成后才发布请求内缓存，之后按原顺序重放。缓存保留 equip1/equip3 类序列及具体匹配，不把两种槽位的多重集合并，也不存助战来源或完整上界。空结果同样可缓存；单一助战组合不分配缓存，准备期已有列表直接复用，流式路径在缓存逻辑之前返回。设助战选项乘积为 `S`、接受的自有组合数为 `U`，完整组合仍为 `M=S×U`，自有枚举/匹配从 `S` 遍降为一遍，上界与精确 DP 不变。额外索引/选择对象为 `O(U)`，只读选择数组可由组合共享；物化分流保证 `S>1` 时 `M≤20,000`，否则 `M≤250,000`，不放宽原存储边界。首次种子不等待额外预生成，收集/评分检查点继续生效；取消时未完成缓存随本次遍历释放，不跨请求复用。

精确从者 DP 的状态表仍是 `(mask, COST)` 稠密数组，每处理一个从者 ID 先复制状态表；另以每个 mask 的分段 COST 位图记录非空单元，只遍历上一 ID 阶段可达的转移源。位图同样保留上一阶段快照，当前 ID 产生的状态只能在下一 ID 阶段使用，包含 COST 为零的选择。每字使用 31 位，使 JavaScript 的有符号位运算下字值和分离出的最低位保持正数；按 mask、字和位递增遍历，与原 mask/COST 顺序一致。严格更高分才替换，故各单元的同分代表与最终回溯路径保持原规则；负分可达状态也必须保留。最终 winner 扫描、空位/强制位判断和 COST 同分规则不变。额外位图空间为 `O(2^F × ceil((C+1)/31))`；它减少不可达源的扫描，不删除稠密状态复制、不减少评分更新，也不改变 DP 的最坏时间/空间阶数。

### 4.1.1 有界内存的流式 CE 分支定界

小组合继续使用前述全量上界排序；探测超限或显式指定 `useStreamingCeFirst` 的可分离问题，按“助战选项→equip1 多重集→equip3 多重集”深度优先遍历。礼装类按启发式排列后，各槽类型保持该排列下类序号非降，仍各自完整覆盖所有无序重数组合；停止扩展代表剩余槽位为空。equip1/equip3 共用容量，助战身份规则不变。深度最多为助战数加两类自有槽数，不随组合总数增长。

前缀保存实际来源向量、COST、类用量和已选 CE 索引。按每个轮廓的 rate/value 分别预排序自由礼装类，同时保留原规范枚举序号；这些排序只用于上界，不改变搜索顺序。对每个槽种、轮廓和字段，贪心取剩余槽数以内的最高非负贡献，跳过该槽种规范后缀之前的类。受限类的可用重数至多为 `identityCapacity-counts`，普通可重复类按所需槽数截断；equip1 另跳过单张 COST 已超过剩余预算的类，equip3 始终免费。进入 equip3 枚举前，其后缀仍从零开始，不能套用 equip1 已经过的序号。零包含剩余槽为空；空后缀及耗尽容量不增加贡献。

equip1/equip3、各轮廓、rate/value 分别借用剩余容量，仍可能重复借用同一资源；忽略跨类共享身份、equip1 多张合计 COST 与来源兼容性。每个未知助战仍独立取其选项逐轮廓最大值。因此每个分量均不低于任一合法补全，加上实际前缀后，通过非负 first、单调 cap/floor 以及每位置最大值继续形成安全上界。完整组合必须先匹配自有身份，再调用原精确从者 DP，才能更新 best。预排序准备为 O(RK log K)、空间 O(RK)，每次来源上界最坏 O(RK)，通常在剩余槽已满足时提前停止；这增加单节点工作，必须以整次搜索收益决定是否保留，不采用每节点动态背包。

有自由 Grand equip3，且存在多个助战选项或无预算多候选重访时，可在本次流式搜索内缓存最多 4,096 个完整自有身份匹配。键保留有序 CE 类序列，固定身份/候选域为请求不变量，来源向量与助战身份池不影响该匹配。用带前导位的进位编码保留顺序和长度；仅当所有可能键都不超过 JavaScript 精确整数上限时使用整数，否则回退完整分隔文本，不使用可能碰撞的摘要代替状态。成功 ID 列表只读保存，不可行结果用独立条目表示，不能与缓存未命中混淆；满表后停止新增并继续正确计算，空序列直接返回。普通无 equip3 请求直接调用原匹配器，不分配缓存或构造键。缓存不改变匹配代表、遍历、预算或证明状态；额外空间按最多 4,096 份长度不超过自有槽总数的序列计，文本键回退另保留完整键，不是固定字节上限。

证明轮 `upper <= best` 即可剪枝，所有剩余子树均被安全排除或搜索穷尽才证明。评估预算只计实际从者 DP 调用；预算耗尽且仍有未排除分支时返回未证明。分支排序只帮助尽早获得可行下界，不参与证明，也不丢弃低优先级分支。主线程分片和 worker 使用同一可恢复流程。

首次证明立即发布，之后先生成最佳见证的从者邻近候选，再用独立的 `(maxTies + maxCandidates) × 4` 次评估额度补充已发现候选；显式评估预算的同步/异步调用不再额外评估礼装组合。补充搜索可用当前保留列表最低分剪枝，额度截断不撤销最高分证明，也不宣称候选全球排名或同分枚举完整。

流式路径没有可报告的精确组合总数，`possibleCombinations` 始终为 null；`isCeFirst=true`、`visitedNodes` 仍计精确组合评估次数，不是已访问前缀数。空间为贡献矩阵、有限结果、top-F 分组元数据、DP 状态及当前 DFS 路径，不保留 O(M) 组合数组。它控制组合存储，并不保证任意实例在多项式时间完成；单步匹配、DP 和真实设备响应性仍需测量。

### 4.2 状态与搜索顺序

每个搜索位置由独立固定维度生成合法 item：自由从者 × 固定/自由 equip1；固定从者的允许灵基 × 固定/自由 equip1 × 固定/自由 equip3；助战仅固定/自由 equip1（以及允许的固定 equip3）。item 记录 COST、候选 ID 集、接收轮廓、位置自身效果和对各目标轮廓的全队贡献。搜索顺序可按分支数与全队影响排序，与编队显示顺序无关。

DFS 状态为已选 item、已耗 COST、每类使用次数和当前来源贡献。种子搜索优先填入从者，再按低 COST、少佩戴礼装尝试，最多访问 20,000 个种子节点；找到首个具体 ID 可匹配的合法队伍就立即回传，不等待局部改进。之后最多两轮、合计 4,096 次 item 尝试做局部替换。此阶段只提供真实可行的下界，不占证明搜索的节点预算，也不能代替完整空间的证明。随后候选按乐观得分降序搜索；在尚无首解时对部分分配也检查身份匹配，避免等到叶节点才拒绝已冲突的前缀。找到首解后按下述身份域风险选择性检查前缀，最终叶节点身份检查始终保留。更高分回传受时间节流，首解不受节流。

#### 容量检查的需求重数

从者类先检查是否仍有一个名额。实际编队 item 至多包含 equip1/equip3 两件自有礼装：无礼装直接通过礼装容量检查；单件检查一个剩余名额；两件属于同类时一次检查剩余容量至少为二，不同类则分别检查各一个名额。这些分支不构造临时需求 Map，也不为 item 保存需求缓存；超过两维的抽象 `BondSearchProblem` 输入继续使用完整重数统计，不截断。进入/退出选择仍按原始索引列表逐件增减，因此类重数、回溯、固定/重复礼装及助战独立容量的语义不变。实际编队的容量检查为常数时间、常数额外空间；不改变候选池、搜索顺序、身份匹配、上界或节点数。

#### 选择性身份前缀检查

请求内分别为从者、受限自有礼装建立完整的规范身份集合，礼装先映射等价组；两种身份命名空间独立。相同集合共享域信息，临时按类缓存只有在完整集合相等时复用，不能仅凭类索引或哈希断定等价。域的每次出现若都消耗同一个类容量，且该容量不超过域的身份数，则同域重复用量已经被容量检查保护。

若一个域的身份数不小于全问题该命名空间的最大维数，任何包含它的 Hall 子集都不会缺身份，可从风险判断中排除。其他域若与不同域不相交、且受上述类容量保护，也无需额外匹配。该分类只决定是否提前检查，不改候选池、类容量、评分、上界或展示计数。

首解前保留原先完整前缀匹配。首解后，无风险请求走直接递归路径；新增风险域时只检查当前前缀：同域出现次数超过身份数可直接拒绝；不同风险域确实相交时才运行既有增广匹配。每次丢弃临时分配，后续仍可增广重分配。没有提前拒绝的最终节点始终重新匹配具体 ID 后计分。故新增剪枝仅排除已无法实例化的前缀，不把贪心分配或简单总体并集大小当作可行性证明。

风险元数据按请求重建，不跨数据更新复用，也不缓存子树结果。构建和遍历均保留分片检查点。它有静态准备成本，适用于跨类 ID 或礼装身份重叠密集的空间，不能保证所有输入加速。

### 4.3 安全上界

对每个剩余来源位置 `p` 与每种接收轮廓 `r`，预计算该位置所有候选可提供的最大非负 rate/value：`M[p][r]`。此最大值忽略 COST、容量与和其他位置的兼容性，因此不会低估任何真实续解。

已确定的接收位置：用已选来源的真实贡献，加上每个未选来源的 `M[p][r]`，得到该位置的乐观分数。实现还按礼装等效类容量给未知来源构造另一上界，两者取较小值。每个 item 只按其第一件受容量限制的礼装分组；这会放松其他容量限制，因而不会低估。未确定的接收位置：对每个候选 item 预计算它在其他来源均取乐观最大贡献时的 `U[position][item]`，再用按位置和剩余 COST 建立的 multiple-choice knapsack DP 求和；DP 故意忽略共享 ID 与容量。

仅在该乐观 DP 内，对同位置、同 COST 的 item 取最大的 `U` 作为一条转移；因为它们访问同一剩余预算的尾表，`max(U + tail) = max(U) + tail`，故每个 DP 单元与完整 item 转移严格相同。负分须保留，不能用零初始化最大值；超过整张表预算的 COST 不进入转移，未能选满所有位置的状态仍为不可达。真实搜索列表、来源贡献、身份域及容量检查完整保留，不能据此删除同 COST 的真实候选。设总 item 数为 `I`、各位置预算内不同 COST 数为 `D[p]`、有效预算为 `C`，DP 构建从 `O(C × I)` 降为 `O(I + C × ΣD[p])`；表空间仍为 `O(位置数 × C)`，当前行额外使用 `O(max D[p])` 的压缩转移。候选评分、排序和搜索复杂度不因此改变。聚合和 DP 转移继续提供分片检查点。

位置与前排开关在搜索前已确定，因此第一乘区 `first = floor(baseBond * (1 + frontlineRate/1000))` 可按手动页精确预计算。乐观第二乘区使用 `ceilDiv(first * (1000 + min(rateUpper, cap)), 1000)`，再加 `valueUpper`；`first >= 0` 使它随 `rateUpper` 单调不减。未知来源的 rate/value 分别取逐项最大值，即使它们来自不同候选也仍是安全上界。DP 的成本索引只使用非负 COST。完整节点上界是“已确定位置乐观分数 + 剩余位置 DP 分数”。两项分别逐位置不低于真实得分，故其和不低于子树最优值。只有 `upperBound < bestFeasibleScore` 才能为了求同分而剪枝；只求最大值时允许 `<=`。

前排与后排分别建立对称类：位置的前排倍率、固定维度、每位置自定义加成、助战性质和 Grand Board 能力均相同时，强制选项类序号非降。不同 profile 不互换；这保留位置特有加成。结果展示时再映射回原槽位。

### 4.4 伪代码

```text
prepared = prepare(request)                     // 完整效果矩阵与等效类
best = feasibleSeed(prepared)                    // 低成本构造 + 两轮局部改进；必须匹配具体 ID
dp = optimisticCostDp(prepared)                  // 忽略共享容量的安全上界

search(k, state):
    if k == numberOfSearchPositions:
        witness = matchServantsAndFreeRestrictedCeIds(state, reservedCeIds)
        if witness == none: return               // 无效类解不得更新 best
        score = scoreExactlyLikeManual(witness)  // 两次 floor，茶壶 ×1
        updateBest(score, witness)
        if collectingTies: updateEffectGroup(score, witness)
        return

    if best != none and upperBound(k, state, dp) <= best.score:
        return                                  // 最大值证明轮；同分轮改为 <
    for item in orderedItems[k]:
        if item.cost > state.budget: continue
        if classMultiplicityExceedsCapacity(item, state): continue
        if violatesSymmetry(item, state): continue
        next = state + item
        search(k + 1, next)
```

`matchServantsAndFreeRestrictedCeIds` 分别匹配自有从者与自动受限礼装；固定从者仍占从者身份，固定受限礼装在预处理验证后占用对应身份。助战使用独立身份池。必须在更新 best **之前**运行。若一项同时自动选择两件同类受限礼装，容量检查按重数 2，而不是分别检查两次 `remaining > 0`。

### 4.5 正确性说明

**完整性**：每个真实可行队伍的从者灵基、礼装版本及固定维度都至少映射到一条搜索路径；等效类只合并在所有可能目标与来源上的效果完全相同的成员。对称规范化只删去相同位置 profile 的排列。因此每个可行分数至少保留一条路径。

**可行性**：预算、固定维度和容量先检查；叶节点匹配给出从者互异、受限礼装身份不冲突且允许的固定副本完整保留的见证；精确评分只对见证队伍运行。故 best 永远是实际可行队伍的分数。

**上界**：每个未知来源的 `M` 独立最大化，只会增加每个接收位置的可得效果；成本 DP 再放宽共享容量与 ID 约束，只会增加可能值。第一乘区与手动页相同，第二乘区向上取整不低于其 `floor`。因此被剪去的子树不可能达到更高分。若未因资源上限中断，best 等于全局最优。

## 5. 同分、跨分数候选与中断

分数证明与同分枚举分开记录：`provenOptimal` 只表示最大分数已证明；`allTiesCollected` 仅表示搜索路径中的同分**效果组**是否收集完整，不表示类内具体 ID 排列已穷尽。通用搜索在最大分证明后另跑有独立节点预算的同分轮；礼装优先路径先报告分数证明，再评估最多 `maxTies × 4` 个上界仍可同分的礼装组合，并始终标记 `allTiesCollected=false`。同一组保留 COST 较高的代表。展示前统一规范化自由礼装：在效果、COST 与助战行为一致的类内，受限礼装按最小可用身份选取所需数量，并避开固定占用；普通 5%／2.5%／2% 则选择最小可用代表并可重复使用。所有自动代表均须跳过排除和未实装项。助战独立选代表。每个显式等价组及指定受限 ID 的容量为一；普通可重复类只按装备槽数截断容量。

自有自由 equip1 只在保持全队效果与总 COST 的位置间排列，顺序为特性要求优先、比例降序、固定值礼装靠后、ID 降序；固定礼装、助战与 equip3 保留位置。所有已选自由自有礼装均为与佩戴者无关的全队效果，因此前后排间安全重排也不改变任一从者得分。重排同步更新每位置 COST 与候选元数据，规范化先于最终候选去重。候选扩展不再产生只改变通用礼装 ID 的队伍。

通用路径按每个位置的接收轮廓与实际羁绊值归类；礼装优先路径还把全队来源效果向量纳入键。通用路径的分数证明轮会顺带记录有限的可行候选，证明后才收集同分效果组；礼装优先路径在证明轮可顺带收集已评估组合的效果组。`ties` 保留最高分的有限效果组代表，默认上限 20（同步 API 可通过 `maxTies` 调整）。它不代表所有同分具体队伍。

页面另用 `FormationBondOption.maxCandidateTeams` 控制 `candidates` 上限，默认 100，可设置 1–200。搜索遇到的每个候选都先匹配具体 ID，再按真实公式计分；列表按分数降序、同分时按 COST 降序保留。证明阶段不从根节点专门搜索同分队伍，优先寻找更高分并证明最高值。进度页先立即展示一支详情完整的合法队伍；之后约每 2 秒，从已发现的种子中补充最多 10 支完整候选，逐步达到上限。补充时先展开当前最高分的同效果代表，再用已发现的较低分队伍及其代表补足；每次新增都需满足具体身份与真实计分规则。普通进度保留此前已展示的候选，按分数、COST 排序淘汰超限项，不缩回一队。礼装优先路径在证明后才展开最高分见证的邻近队伍，并额外评估最多 `maxCandidateTeams × 4` 个组合；有显式评估预算且已证明的同步调用也会展开该见证的邻近队伍，但不额外评估礼装组合。通用路径在证明后最多再访问 100,000 个节点收集候选。即使额外收集被预算截断，`provenOptimal` 仍只表示最高分已证明。证明后，对种子队伍还可轮流替换单个从者或定向礼装为同效果类的具体 ID；每个替换都重新检查自有从者 ID 与受限礼装身份约束，保持该队伍的分数和 COST 不变。候选列表只表示**已发现队伍中的前 N 个**，不证明第 2、3 档的全球名次，也不保证凑满 N 个。

达到搜索预算时立即返回最佳已知可行队伍与 `provenOptimal=false`；若尚无可行见证，返回 `best=null` 且 `provenOptimal=false`。若搜索穷尽而无见证，则 `best=null` 且 `provenOptimal=true`。交互页不把预算用作最终停止条件：先显示最佳已知队伍，再继续求证，用户取消时保留已显示候选及此前已获得的证明结论。

1. 将每一种 scope、佩戴者/目标条件、RateCount/AddCount、cap、两次取整、助战 followerVals、活动优先级与 campaign 扩展为独立规则测试。
2. 扩大小候选池的具体 ID 穷举 oracle，覆盖跨灵基同 ID、同类多件礼装、仅固定礼装、固定与自由 Grand Board、无效定向礼装、前排对称和 COST 边界；礼装优先快路径还需覆盖可分离判断的正反例。
3. 加入变形性质：提高预算或放宽候选过滤不应降低已证明最优值；每个输出见证须 COST 合法、具体 ID 互异，且能用权威公式复算。
4. 性能基准分别记录数据预处理、礼装组合生成和上界排序、从者 DP、具体身份匹配与结果归类的耗时；通用回退另记 DFS 节点数。在典型与极端 Quest 上测量后再设交互时间目标。不得以提高搜索预算代替正确性验证。

### CE 算法的直接回归入口

`ce_source.dart` 封装与佩戴者无关的 CE 来源及规范后缀/剩余容量贡献界；`ce_identity.dart` 封装受限身份匹配、原序代表重建和有界匹配缓存；`ce_assignment.dart` 封装按具体 ID 的 0/1 分配 DP 及请求内精确缓存。三者只接收已解析的纯数据，不访问 Flutter、Quest 或游戏数据库。`ce_first.dart` 和 `ce_stream.dart` 继续负责各自遍历与业务结果组装，缓存启用条件仍由搜索控制。

`ce_algorithms_test.dart` 将 `ce_algorithm_cases.dart` 中的同一套独立穷举/边界检查纳入正常测试；后者还可直接在 Dart VM 与编译后 JavaScript 运行，不再抽取或替换生产源码。真实数据规则、三路径差分、取消及结果发布仍由原测试负责。历史实验模板与对应源码另行归档，不属于当前验证入口。

## 8. 性能边界与后续优化

Grand equip3 或多助战会使礼装组合数相乘。当前用按礼装类和两种槽位计数的 DP，纳入每类容量及 equip1/equip3 的共享用量，再乘助战选项数；普通可重复类只受槽数限制。该上界仍忽略跨类身份重叠和 COST。助战选项乘积大于一时使用 20,000 的物化阈值，否则使用 250,000；超过所选阈值时先执行有界的自有礼装探测，实际未超限则复用已匹配身份的组合，超限改用流式 CE 分支定界。助战选项本身的乘积超过上限时直接选择流式路径。这个阈值只选择 CE-first 的物化或流式路径，不限制搜索运行时间，也不改变 `provenOptimal` 的含义。 探测在正式搜索前完成，不运行从者 DP、不消耗组合评估预算、不产生可行队伍或证明。探测截断后从原预算开始流式搜索，不能当作无解；取消通过共用调度检查。500,000 是枚举条目/检查点上限，不是墙钟或单次匹配耗时保证。结果中的 `visitedNodes` 在礼装优先路径表示已评估组合数，在通用路径表示已访问节点数，不能直接横向比较。

预处理仍在 UI isolate，但 `BondWorkScheduler` 约每 10ms 计算后通过约 16ms Timer 让出输入与绘制事件。预算是目标，不是单步骤或实机 30Hz 的硬保证；Debug 日志记录阶段耗时、最长步骤和让出次数。原生主体搜索继续使用 worker；Web 用同一生成器流程续接组合枚举、稳定归并排序、从者 DP、准备与 DFS，不重复搜索。 礼装组合枚举在组合入口及递归循环中设置独立检查点，不依赖接收者评分；满羁绊、COST 超限或身份匹配失败时仍能让出执行时间。

主线程结果转换与灵基详情也分片执行。首个合法见证单独保留，不能被普通进度或最终快照合并覆盖；该队伍的灵基详情齐全后才发给 UI。首队发布后启动定时补充（生产默认 2 秒，测试可缩短间隔），每批最多新增 10 支；普通快照复用此前队伍及其灵基详情缓存。补充与主线程搜索都按时间预算分片，不改变搜索核心的证明顺序。首次最高值证明优先随当前已完整准备的队伍发布，保留此前展示的候选，然后再转换更多候选；若它已是最终快照，仍另排一次完整候选转换，避免丢失结果。其余尚未转换的旧快照可以合并，保留最终证明、结束和错误状态。原生 CE-first 回传的首解与首次证明绕过常规节流。组合总数未准备完成时为 null，`isCeFirst` 独立标识算法，不把“总数未知”误判为通用搜索。Debug 记录首解的搜索发现时间、主线程收到时间、首支完整队伍与首次证明的发布时间，以及转换、灵基详情和礼装上界准备耗时，页面进度日志同时记录候选数。首次证明、搜索结束、错误或取消时停止补充定时器。具体队伍缓存键包含位置选择、分数、COST 和候选元数据，有容量上限，复用队伍与灵基判断。进度通过局部 ValueListenableBuilder 更新结果和操作条，不反复重建输入区域。运行活动条有 5 段，每约 250ms 离散切换高亮，1→2→3→4→5→1 循环，无平滑补间，不表示百分比；取消使用 FilledButton。

旧版在 2026-09-16 数据上的秒数与节点数只适用于当时的代码和编队，不能作为当前性能保证。实机流畅度由人工审核，后续优化基于分阶段耗时。

`temp/fgo-calc/README.md` 与 `backend/internal/service/calculator.go` 是算法参考：它枚举礼装组合，并对从者作 COST 背包，还以同 COST 无条件礼装构造优先级链。其问题定义明确不考虑本求解器的前排倍率，而且其从者前 `k` 筛法、15 绊修正、支持效果与具体 ID 处理均须在本需求条件下重新证明，不能整段移植。
